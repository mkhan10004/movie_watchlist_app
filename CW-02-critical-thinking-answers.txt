CW-02 Critical Thinking - Undergraduate Answers

1. Navigator Stack Mental Model

When the app first opens, the Navigator stack contains only HomeScreen: [HomeScreen]. When I tap a movie, Navigator.push() adds DetailsScreen above it and passes the selected Movie object: [HomeScreen, DetailsScreen]. Pressing Back pops DetailsScreen and returns to HomeScreen. The assignment's WatchlistScreen is a graduate-only feature and is not currently in my app. If I added it and opened it from HomeScreen, the stack would be [HomeScreen, WatchlistScreen]; opening it from DetailsScreen would make the stack [HomeScreen, DetailsScreen, WatchlistScreen]. Understanding the stack helps me predict what Back will do and avoid replacing a screen when I intend to add one.

2. StatelessWidget vs StatefulWidget

I used StatelessWidget for DetailsScreen because it receives a Movie and displays its title, poster, cast, and synopsis without changing its own data. The screen's content is determined by the movie passed to its constructor. A StatefulWidget would be needed if I added a changing control, such as a watchlist toggle, that updates the interface while the screen is open. My rule of thumb is to use StatelessWidget when a screen only displays the data it receives, and StatefulWidget when it must manage changing UI state. State could also be managed higher in the widget tree or with a state-management package if multiple screens need to react to it.

3. Data Architecture: Model vs Hard-coded

I use a Movie model to keep each title, poster path, cast list, and synopsis together. The sample movie records are kept separately from the screens, and HomeScreen passes the selected movie to DetailsScreen. This avoids hard-coding each movie's details into the screen and makes it easier to add or update movies without duplicating display logic. It also gives both screens a consistent structure for movie data. If I connected the app to a REST API, I would add a way to convert JSON responses into Movie objects, likely with a fromJson constructor or a data repository. I would also need to handle loading, network errors, and possibly missing fields instead of relying only on the current local sample list.

4. Asset Management in Flutter

I put the poster image files in assets/images/ and declared that folder under flutter: assets: in pubspec.yaml. I then use each movie's posterPath with Image.asset() in the screens. The declaration tells Flutter to include those files in the app's asset bundle; without it, the app may not find them at runtime. One common problem is a path or filename mismatch, including capitalization. I would compare the string in the movie data with the exact file path. Another problem is forgetting to run flutter pub get after changing pubspec.yaml; I would run it and hot-restart the app. I would also check the debug console for asset-loading errors and confirm that the image file exists in the project.

5. UX Design Decisions

On HomeScreen, I used a light background with a blue/purple primary color and white movie rows. Each row places a fixed-size poster beside the title and cast, with a chevron to suggest that tapping opens more information. On DetailsScreen, I placed a larger poster first, followed by the title, cast chips, and synopsis in a scrollable layout. I used the same primary color in both screens to keep the app visually consistent. The poster and title establish visual hierarchy, while the tappable list rows and chevrons make navigation apparent. If I had more time, I would improve accessibility with stronger contrast checks and screen-reader descriptions for posters, and test the layouts on more screen sizes. I would also consider adding movie genres or release years to help users scan the list.

6. State Persistence and Scalability

The current undergraduate app does not implement a watchlist, so there is no watchlist state to persist. If I added one, shared_preferences could store a small list of saved movie IDs or titles locally. It is relatively straightforward for simple settings or small amounts of data, but it is not designed for complex queries or larger structured collections. A local database such as sqflite would let me store movie records and watchlist relationships in tables, then query or update them more flexibly. That adds database setup and schema-management work. For a small feature, preferences may be simpler; as the app grows and needs structured queries or more records, a database would be a better fit.

7. Git Workflow and Commit Culture

A continuous commit history shows how a project developed and makes individual changes easier to understand, review, and undo. When I checked this project folder, it had no Git repository or earlier commits, so I cannot honestly claim that I committed regularly throughout development. I initialized Git and pushed these two commits: "feat: add movie watchlist app" and "docs: add app setup and release instructions". Both messages describe their changes, but they were created together for this submission and do not demonstrate development across multiple stages or days. A stronger history would have smaller commits as I completed the model, screens, assets, and navigation. That would help an employer see how I organize and explain changes, not just the final result.

8. Beyond the Assignment: Feature Brainstorm

First, I would add search and genre filters so users could find movies more quickly. I could use a TextField or SearchAnchor and filter the local movie list as the user types; this would make browsing easier as the collection grows. Second, I would add a persistent favorites list so users could save movies and find them later. That would require a toggle, a list screen, and local storage such as shared_preferences for a small list or sqflite if the data became more structured. Third, I would add movie ratings and personal notes. A rating control such as RatingBar or a row of interactive icons, plus a text field, would let users remember why they saved a movie and prioritize what to watch.
